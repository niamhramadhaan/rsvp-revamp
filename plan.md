# Event Dashboard (Gamefinity) — pivot plan

## Context

This repo (`rsvp-revamp`) started this session as a generic "task management dashboard" UI clone (crypto-card demo → task-management-style Overview page), built purely as a Tailwind/React design exercise. The user now wants to repurpose it as the real foundation of an **event RSVP / seat-map / check-in dashboard** product for their brand, Gamefinity: Admin creates events, builds a grid-based seat map, imports/adds guests, sends WhatsApp+email invites with an RSVP link, assigns seats independently of RSVP timing, issues QR tickets, and Staff check guests in on event day (with duplicate-check-in blocking, manual search fallback, and no-seat-yet handling). After the event, it archives with an attendance report. Two roles: Admin (full access) and Staff (check-in only, scoped to one event).

Nothing about the current UI is event/guest/seat-aware yet — it's a reusable **visual shell** (design tokens, layout primitives, icon system, modal system) sitting on top of entirely disposable mock content (fake "projects", a fake "welcome" banner, a fake activity feed, etc. left over from the original demo).

## Readiness assessment

**What's genuinely reusable (~the "base" the user is asking about):**
- Design system: Tailwind v4 `@theme` tokens (`src/index.css`), Poppins type, card/pill/shadow conventions.
- App shell: `DashboardLayout.jsx` + `IconRail.jsx` + `TopHeader.jsx` — a responsive admin shell (fit-screen desktop w/ main-only scroll, stacked mobile) with working nav tooltips, notification/profile popovers, and a "coming soon" toast for unbuilt nav items.
- A small reusable component kit: `Modal.jsx` (centered confirm dialog), `Drawer.jsx` (slide-in-from-the-right panel — the dashboard's primary popup pattern for anything richer than a tiny confirm: calendar today, guest/event forms and detail views later), `LogoutModal.jsx`, `CalendarCard.jsx` (real date-math calendar, now opened via the Drawer from a Calendar icon in `TopHeader`), hand-authored inline-SVG icon system (`icons/NavIcons.jsx`, `icons/UiIcons.jsx`).
- Interaction patterns worth repeating: "card header + View All → Modal/Drawer with extended list", outside-click-to-close via invisible backdrop, toast-on-click for not-yet-built nav, permanently-mounted-but-inert (`inert` attribute) popups for smooth enter/exit CSS transitions without an unmount race.

**What does not exist at all yet (i.e. ~0% of the actual product):**
- No routing (no react-router), so no concept of multiple pages/events yet — today's app is a single static "Overview" screen.
- No data layer/persistence — every list is a hardcoded JS array in the component that renders it; no localStorage, no mock API shape.
- None of the domain entities exist: no Event, SeatMap, SeatGroup, Seat, Guest, StaffAccount.
- No seat map grid builder, no guest management/import, no invite sending, no public RSVP page, no QR generation, no check-in scanner, no live counts, no archive/report.
- No auth/roles concept (Admin vs Staff).
- ~~`ProjectStatistics.jsx`, `ProjectDeliveriesChart.jsx`, `WelcomeBanner.jsx`, `ActivityFeed.jsx`'s wiring, `EventsCard.jsx`~~ — deleted/unwired in the Phase 0 cleanup that shipped alongside this plan. `ActivityFeed.jsx` itself is kept as a copy-from pattern (see below).

**Bottom line:** you have a solid, on-brand-able visual shell and a couple of genuinely reusable primitives (Modal, Calendar, icon system) — call it the "chrome" of the app. None of the actual event-dashboard *product* exists yet. Realistically this is early-stage scaffolding, not a partially-built feature set.

## Nothing OS widget style — analysis and fit for this design

The user shared a reference image (`Nothing Widgets - 2.0.png`) of Nothing OS's home/lock-screen widget system, asking whether this visual language is worth using in the Gamefinity dashboard.

**What the reference actually is, structurally:**
- A disciplined **bento grid** of tiles on a shared corner-radius/size grid (1x1, 2x1, 2x2 units) — only two tile shapes appear: **circle** (simple binary toggles/single icon+label — Bluetooth, Airplane mode, Auto Rotate) and **rounded-square/squircle** (anything with more than one line of content — multi-stat, photos, charts, lists).
- A strict **three-color palette per tile**: pure black, pure white, or one saturated **red** accent — never mixed, never gradient. Red is reserved specifically for alert/active/urgent states (REC, Do Not Disturb, "X over limit," camera/mic/location-access warnings) — everything else is plain black-on-white or white-on-black.
- **Content hierarchy is almost entirely size-based**: one big bold number or word dominates each tile (`5,543`, `34°`, a bare `29`, `40 MIN`), with a small caption underneath in tiny uppercase/mono type. Minimal chrome, no borders, no icons-plus-labels-plus-values competing for attention.
- Photography tiles (album art, a photo) get the **exact same tile treatment** (same radius, same grid slot) as an icon/text tile — a photo is "just another widget," not a special case.
- A distinctive **dot-matrix ("glyph") typeface and dot-grid pixel iconography** — a running figure, sound waves, a heart, are all rendered as clusters of dots rather than solid icons; the weekly step-activity strip is dot-clusters, not a bar/line chart. This is Nothing's specific brand signature (their "Glyph"/Ndot identity), not a generic bento-grid technique.

**Where this genuinely fits our upcoming work:**
- **Staff check-in result card (Phase 6)** — the single best fit in the whole product. Nothing's full-bleed color-block alert tiles (red "REC", red "Do not Disturb") map almost exactly onto our planned check-in result states (valid=green, duplicate=amber, invalid/no-seat=red): a huge, bold, single-color full-width tile with the guest's name and seat in giant type is exactly the "unambiguous at a glance, readable from arm's length on a noisy event floor" quality that check-in needs most.
- **Admin live-count dashboard (Phase 7)** — Invited/Confirmed/Declined/Checked-in as a small bento grid of bold-numeral tiles (rather than four generic label+number cards) fits this idiom directly, and these tiles were already planned to double as clickable filters — consistent with Nothing's "one glanceable fact per tile" discipline.
- Our existing circular icon buttons (rail nav, bell, calendar trigger) are already in this spirit — leaning further into circle-for-toggle / squircle-for-content is a small, consistent extension.

**Adapted, not copied verbatim:**
- The strict **black/white/red** palette is part of Nothing's identity; Gamefinity already has a real brand palette. The adaptation: white/light tiles by default, `ink-900` (near-black navy) tiles for emphasis, Gamefinity blue (`accent-700`) as the *single* accent for "active/live" states, reserving red strictly for true negative states (declined/invalid) — mapping directly onto the `status-confirmed`/`status-declined`/`status-pending` tokens already in the theme.
- On the dot-matrix typeface/iconography: **confirmed with the product owner to include this flavor** — big stat numerals in the two slated spots get a monospace/dot-matrix-styled treatment, and simple dot-grid accents are fair game for small supporting icons/dataviz. Guardrail: use a *different* monospace/dot-matrix web font (e.g. something in the "Space Mono"/"JetBrains Mono"/true pixel-font family) rather than literally sourcing or replicating Nothing's own proprietary "Ndot"/Glyph typeface — same technical/gadget vibe, not the identical branded asset. Pick the exact font when Phase 6/7 actually gets built.

**Decision:** adopt, adapted to Gamefinity's palette — bento grid, bold-number hierarchy, single-accent restraint, and a dot-matrix/monospace numeral treatment (using a distinct, non-Nothing font). Scope confirmed: exactly two spots for now — the Phase 6 check-in result card and the Phase 7 live-count tiles — not a wholesale redesign of every screen today.

## Architecture: routing, folder structure, data layer, auth

**Router:** add `react-router-dom` (standard choice for a plain Vite+React app; avoids TanStack Router's type-gen ceremony and wouter's lack of nested layouts).

**Three shells** (today's single admin-only shell doesn't fit a public guest page or a staff-only scanner):
- `AdminShell` — adapted from today's `DashboardLayout.jsx` (IconRail + TopHeader + `<Outlet/>`, same responsive fit-screen/scroll behavior, full-viewport width).
- `StaffShell` — new, minimal top bar (event name + staff name + logout), no IconRail/RightPanel, scanner-first full-screen layout.
- `PublicShell` — new, minimal centered-card layout, no admin nav at all (guest is unauthenticated).

**Routes:**
```
/login                              mock login (role-aware)
/admin/overview                     landing dashboard (today's active nav item)
/admin/events                       Event list
/admin/events/new                   Event create
/admin/events/:eventId              Event detail hub (tabs: Guests / Seat Map / Check-in / Reports)
/admin/events/:eventId/guests
/admin/events/:eventId/seatmap
/admin/events/:eventId/reports
/staff/:eventId/checkin             staff scanner + manual search
/rsvp/:token                        public guest RSVP (no auth, PublicShell)
```

**Folder structure** (extends, not replaces, the existing flat `src/components/`):
```
src/components/   existing reusable primitives (Modal, Drawer, Toast, LogoutModal, CalendarCard, icons/) + a few new generic ones
src/layouts/      NEW: AdminShell.jsx, StaffShell.jsx, PublicShell.jsx
src/pages/        NEW: thin route-level composition, one file per route above
src/features/     NEW: entity-specific meatier UI, grouped by domain (events/, guests/, seatmap/, checkin/, reports/)
src/data/         NEW: store.js (localStorage engine + change-notify pub/sub), seed.js (mock fixtures), entity modules (events.js, guests.js, seatmaps.js, staff.js), selectors.js (derived counts)
src/lib/          NEW: token.js, qr.js, waLink.js, format.js
src/auth/         NEW: AuthContext.jsx, useAuth.js, RequireRole.jsx
```

**Mock data / persistence layer:** every entity module (`events.js`, `guests.js`, `seatmaps.js`, `staff.js`) is the *only* code that touches `store.js`/localStorage, and returns Promise-wrapped results so call sites already read as async — this is what makes swapping to a real API later a localized change instead of a rewrite. `store.js` provides `readTable`/`writeTable` per entity (one localStorage key each), `seedIfEmpty()` (runs once at boot from `seed.js`), `genId()`, and a tiny in-memory change-notify mechanism so multiple mounted components (e.g. the Guests page and the Overview live-counts widget) stay in sync without needing Redux/Zustand. A thin hook layer (`useEvents()`, `useGuests(eventId)`, `useSeatMap(eventId)`, etc.) wraps each entity module in `useState`/`useEffect`, matching the existing per-component-state convention but centralizing the source of truth. Live counts (`invited/confirmed/declined/checkedIn`) are a pure derived selector over the Guest array — never a separately-maintained counter.

**Auth/roles:** a real (if intentionally minimal) mock login at `/login` — admin has one seeded credential, staff logs in against seeded `StaffAccount` rows (plaintext-compare, no hashing/expiry needed for a prototype) which naturally scopes a staff session to one `eventId`. A `RequireRole` route guard wraps `AdminShell`/`StaffShell` routes. Guest RSVP routes need no auth — access is via possession of the unguessable `token` alone.

**Admin nav — decided (Option B, minimal global rail):** `Guests`/`Seat Map`/`Check-in`/`Reports` don't get their own rail items — they only make sense scoped to one event, so they live as **tabs inside the Event Detail hub** (`/admin/events/:eventId`) instead. The rail stays deliberately small: **Overview, Events**, divider, **Settings**, **Log out**. `IconRail.jsx` has already been trimmed to this (dropped the old placeholder Dashboard/Team/Activity/Boost items entirely, along with their icons from use — `GridIcon`/`UserIcon` are earmarked for reuse as the Seat Map / Guests tab icons when those get built, `FlameIcon`/`RocketIcon` didn't map to anything real and are just unused now). Only `Overview` is a real destination today; `Events` still shows the "coming soon" toast until Phase 1/2 give it a route — flip it to a real `NavLink` then.

**Reuse / adapt / delete:**
- Keep as-is: `Modal.jsx`, `Drawer.jsx`, `Toast.jsx`, `LogoutModal.jsx`, `CalendarCard.jsx`, the hand-authored inline-SVG icon convention in `icons/`.
- Adapt: `DashboardLayout.jsx` → `layouts/AdminShell.jsx` (rename+refactor, not rewrite); `TopHeader.jsx` keeps its bell/profile popover pattern plus its Calendar-icon → `Drawer` trigger and a Fullscreen-toggle icon (Fullscreen API, plain icon button — no separate visual block), wires Log out to real `AuthContext.logout()`.
- Already done (Phase 0, shipped with this plan): deleted `WelcomeBanner.jsx`, `ProjectStatistics.jsx`, `ProjectDeliveriesChart.jsx`, `EventsCard.jsx` (name-collided with the real Event entity), `ContactList.jsx`, `BirthdayCard.jsx`, `CryptoCard.jsx`, `IncomeChart.jsx`, `IncomeSection.jsx`, `TransactionsSection.jsx`, `RangePills.jsx`, `SortControl.jsx`, `RightPanel.jsx` (the persistent right-column aside — its only content, `CalendarCard`, now lives behind a `Drawer` opened from `TopHeader` instead of a permanently-docked column), the unused crypto glyphs in `UiIcons.jsx`, the flag-US language indicator (removed per request, along with its asset), and the orphaned avatar/eth-hand/vite.svg image assets. `ActivityFeed.jsx` itself was kept (unwired) as a copy-from pattern (avatar+text+timestamp+"View All" modal) for a future real activity feed. `DashboardLayout.jsx`'s `<main>` now renders a small "Event dashboard coming soon" placeholder until Phase 1-2 land, and its outer shell is no longer width-constrained/centered (`max-w-[1440px] mx-auto` removed) — the rail/header/content now span the full viewport edge-to-edge. Also added: a `Drawer.jsx` primitive (slide-in-from-the-right panel, smooth CSS transitions via a permanently-mounted-but-`inert`-when-closed wrapper) — this dashboard's chosen pattern for calendar/forms/detail views going forward, with `Modal.jsx` reserved for small centered confirmations (like Log out) — and a `Toast.jsx` primitive (stylized bottom-right, fire-and-forget auto-hide notification, same smooth-transition approach) replacing the toast markup that used to live inline in `IconRail.jsx`, so any component can reuse it going forward.

## Domain UX design (per feature)

### Seat map grid builder
- **Grid setup**: rows/columns form with live preview; on save, generates one `Seat` per cell (row-major), `status: 'unconfigured'`, `groupId: null`, `kind: 'seat'`. Growing the grid later (add row/col at edge) is safe; shrinking must block if any removed cell is occupied/assigned — simplest safe rule: **block shrink entirely once any seat is assigned**, only allow growing.
- **Groups & painting**: `SeatGroup` chips (label + color swatch from a fixed on-token palette, not a raw picker) act as the "active paint" tool. Grid is a CSS grid of buttons (no image/canvas). Interactions: click-toggle a single cell; drag-select a rectangle (mousedown→mouseup) to bulk-apply the active group; a non-drag "type start/end row-col" fallback for accessibility/touch.
- **Aisles/gaps**: add `Seat.kind: 'seat' | 'gap'` so walkways/stage/missing seats can be marked, excluded from numbering/counts/assignment.
- **Label generation**: `SeatMap.labelScheme: 'coordinate' | 'group-sequence'`, chosen once at setup — coordinate = "A1"/"B12" from row/col; group-sequence = "VIP-3" incrementing within a group at paint time. Label is **frozen at paint time** (not recomputed on every render) to avoid numbers shifting as painting continues; explicit "Renumber group" action if the admin wants to regenerate.
- **Deleting a group**: cells revert to unconfigured; block if any assigned cell would be orphaned.
- **Reuse**: the same presentational `SeatGridView` component (props: seats, groups, cell-state, click handler) powers (a) the builder, (b) seat-assignment mode (pick a guest, click an empty seat — or vice versa; assignment is never gated on RSVP status), and (c) a read-only "show me my seat" view for staff check-in.
- **Edge cases**: large grids need scroll with sticky row/column headers; empty-state before rows/columns are set; overwriting a cell that's already occupied by a *different* group needs a confirm, not silent overwrite.

### Guest management
- **Manual add** (modal, same form-in-modal pattern as the old EventsCard add-form): name, WhatsApp, email (at least one contact required), group (select from this event's SeatGroup labels **plus free text** — see decoupling note below). Creates `Guest` with a fresh globally-unique `token`, invite channel fields all unsent, `rsvpStatus: 'pending'`, `seatId: null`.
- **Bulk import**: two-step modal — paste/upload CSV → preview table with per-row validation errors → commit. Proposed columns: `name` (required), `whatsapp`/`wa`/`phone`, `email` (at least one of these two required), `group`/`category` (optional, free text), `notes` (optional), `seat_label` (optional — pre-assigns if it matches an existing empty seat). This is a reasonable default per the user's own "mock, adjust as needed" — revisit once real guest lists exist.
- **`groupLabel` is intentionally decoupled from `SeatGroup`**: it's a free-text categorization (e.g. "Family"/"Press"/"Sponsor") that *may* line up with seat-map sections but isn't a foreign key — the add/import UI suggests existing SeatGroup labels as autocomplete options without enforcing them.
- **Guest list table**: Name / Contact (WA+email glyphs, filled vs outline) / Group pill / Invite status (per-channel, see refinement below) / RSVP status / Seat (label or "Assign") / Checked-in (timestamp or —) / row actions (send/resend invite, assign seat, edit, remove). Filters (composable AND): inviteStatus, rsvpStatus, seat-assigned, checked-in, group, free-text search. Live-count tiles double as one-click filter shortcuts.
- **Edge cases**: duplicate contact → warn, don't block (real events have duplicate names); no contact info at all → block send actions, show warning badge; removing a seated guest → confirm + free the seat; removing an already-checked-in guest → soft-delete only (`Guest.status: 'active'|'removed'`), never hard-delete, to protect the attendance report's history.

### Invites (WhatsApp + email) — honestly mocked, not fake-realistic
- Per-guest **two independent send actions**, not one combined button: "Send via Email" builds a `mailto:` link (subject+body from a shared template: event name/date/venue/description + `{origin}/rsvp/{token}`, explicitly no seat number); "Send via WhatsApp" builds a `https://wa.me/{number}?text=...` deep link. Both just open the OS mail client / WhatsApp with a pre-filled message — the admin still hits send themselves. This is deliberately honest about what a frontend-only phase can do; no fake "delivered" receipts or progress spinners.
- Clicking either marks that channel `sent` immediately (meaning "handed to the admin," not "delivered") with a small UI disclosure to that effect. Resend is just re-showing the same buttons with a "last sent at {time}" caption. No fabricated delivery-failure detection — a manual "mark contact invalid" action covers the real failure case (bad number/address).
- Bulk sending across N selected guests: a "next guest" stepper modal (not N auto-opened tabs/windows, which browsers block) — shows one guest at a time with both send buttons and Skip/Next.
- **Refinement**: `Guest.invites: { wa: {status, sentAt}, email: {status, sentAt} }` replaces a single `inviteStatus` field; an overall "invited" boolean is derived (`wa.sent || email.sent`), not stored.
- Flag clearly (in-app helper text + this plan): real delivery tracking needs a backend (WhatsApp Business API / SendGrid-style service) and is out of scope until/unless a backend exists.

### Public RSVP page
- Route `/rsvp/:token`, rendered in `PublicShell` — **no admin nav at all**, safe to share publicly, self-contained.
- Card layout: event name/date/venue/description, personalized greeting via guest name, **no seat info** (matches spec). Two actions: Confirm attendance / Can't make it.
- States: invalid/unknown token → simple error message, no form. Already responded → show the confirmation state directly, with a "Change your response" link (real guests do flip their answer — must stay idempotent/re-enterable, not one-shot). Event already archived/past → read-only "already took place" message.
- After responding: same page swaps to a confirmation view (not a separate route, to keep token context) — "You're confirmed"/"Thanks for letting us know" + repeated event details. Once a seat exists, this same page can grow a "Your ticket" section (QR + seat label) later rather than inventing a third public route.
- Data flow: resolve `token → Guest` globally (token must be unique across *all* events, since the URL carries no eventId) via a `useGuestByToken(token)` hook; write `rsvpStatus` + a new `respondedAt` timestamp.

### QR ticket + staff check-in
- QR becomes generatable only once `Guest.seatId` is set. Encode the **token alone** (same identifier the RSVP page already resolves) — no HMAC/signature/expiry for this prototype; call this out explicitly as a known limitation for a future real backend (rotating/short-lived codes, ticket-transfer prevention). **Round 10 — Emil Kowalski design-eng review, then implemented.** Reviewed the whole app against Emil Kowalski's UI-polish/animation philosophy (the `emil-design-eng` skill). Findings, now fixed:
- **No `:active` press feedback anywhere.** Every button in the app (rail nav, header icons, quick actions, tabs, calendar nav, every dialog's Cancel/Confirm/Close) was silent on press. - **Four popovers had zero enter/exit animation**: `TopHeader`'s notifications/profile menus, `EventSwitcher`'s event list, `GlobalGuestSearch`'s results — all just hard-cut via `{open && (...)}`. Extracted the `entered`-lags-one-frame trick (already duplicated identically in `Modal.jsx` and `Drawer.jsx`) into a shared `src/hooks/useEnterTransition.js`, and used it to bring all four in line with `Modal`/`Drawer`'s pattern: permanently mounted, `inert` when closed, `scale-95 opacity-0` → `scale-100 opacity-100` at 150ms ease-out, with `transform-origin` set to the actual trigger corner (`origin-top-right` for the right-aligned header menus, `origin-top-left` for `EventSwitcher`, `origin-top` for the full-width search results) instead of the meaningless default center.
- **`transition-all`** on `Toast.jsx` and the `IconRail` tooltip → narrowed to the actual animating properties (`transition-[opacity,transform]`).
- **`RsvpBreakdownChart`'s segments animated `width`** (a layout-triggering property, and a real instance of the exact anti-pattern behind this whole session's lag investigation). Rather than reworking it to a `transform: scaleX()` equivalent (real complexity for a 3-segment bar, since a clean interpolation would need to track the previous proportion), removed the transition entirely — this is precisely the skill's own "functional graph in a banking app, no animation would be better" case: it's live data, not decoration, and shouldn't animate on every change regardless of which property it'd use.
- **No `prefers-reduced-motion` handling anywhere.** Added a blanket `@media (prefers-reduced-motion: reduce)` rule in `src/index.css` collapsing all transition/animation durations to near-zero — every animation in the app is transform/opacity-based, so this is a safe, correct baseline (state still changes, just instantly instead of animating).

**Round 21 — page background fixed (root cause, not patched), seat map responsive to the drawer, drawer panel made a "block."** Three asks.
- **Background: not full-screen, and too faint.** Root cause of "not full screen": `GradientBackdrop.tsx` (round 11) was a `position: absolute` decorative element living *inside* `#dashboard-main` — the very thing it was scrolling alongside, not scrolling relative to. Its `-bottom-[N%]` placements were sized against `<main>`'s own rendered (viewport-fit) box, not the full scrollable content height, so once you scrolled down through a data-heavy page it simply scrolled up and out of view, leaving the rest of the page backgroundless — exactly "not full screen." (`position: fixed` was deliberately avoided for this back in round 11, per its own comment, because a fixed decorative child has no inherent clipping and could bleed over the opaque `IconRail` sidebar.) Fixed by deleting `GradientBackdrop.tsx` entirely and moving the wash onto `<main>`'s own CSS `background` (`DashboardLayout.tsx`) with `background-attachment: fixed` — a background is *always* clipped to its own element's border box by definition, so it can never bleed over the rail the way a stray positioned child could (resolving round 11's exact worry for free), while `fixed` attachment keeps it anchored to the viewport instead of scrolling away, so it now genuinely covers all of `<main>`'s visible area regardless of scroll position. (Noted caveat: some older mobile Safari versions degrade `background-attachment: fixed` to plain `scroll` — ugly but not broken.) Also addressed "looks like no color": the three stacked radial-gradients' `color-mix` alpha values went from a barely-there 4–14% up to a clearly-visible 20–26%, still restrained enough to keep foreground text/card contrast intact but now unmistakably Gamefinity blue/cyan rather than reading as flat white.
- **Seat map canvas not responsive to the drawer.** Root cause: `GuestSeatingView`'s guest-list/seat-map split (and, it turns out, three of `OverviewContent`'s own paired-widget rows) used Tailwind's plain `lg:` prefix — a *viewport*-width media query — to decide when to go two-column. But opening a drawer alongside them doesn't change the viewport; it shrinks `#dashboard-main`'s own rendered width via the push/reflow grid track (`DashboardLayout.tsx`). `lg:` has no way to know that happened, so these layouts stayed locked into their wide two-column shape and got visibly cramped (the seat map worst of all, being the most complex/dense one) whenever a drawer was open next to them. Fixed with Tailwind v4's built-in container queries instead of viewport ones: `<main>` gained `@container` (`container-type: inline-size`), and every affected `lg:grid-cols-*`/`lg:items-start` in `GuestSeatingView.tsx` and `OverviewContent.tsx` switched to `@5xl:` (Tailwind's named container-query variant for 64rem/1024px — the same numeric threshold `lg:` used, chosen so behavior is unchanged whenever no drawer is open) — confirmed in the built CSS (`@container (width>=64rem){...}` rules, not `@media`). These now react to the space `<main>` actually has, drawer or no drawer.
- **Drawer panel made a "block," matching `<main>`'s own glass-stage card.** `OverviewContent`'s widget stack sits inside one large rounded/bordered/shadowed block (`rounded-[2rem] border border-white/40 ... shadow-[...]`); `DrawerPanel.tsx`'s desktop push/reflow panel, by contrast, was a flush, square-cornered rectangle sitting edge-to-edge in its own grid track. Gave it the matching treatment at `lg:` only: `lg:p-4` on the outer `<aside>` (creating the visible gap around it — the actual thing that lets it read as a floating block rather than a flush panel) plus `lg:rounded-[2rem] lg:border lg:border-black/5 lg:shadow-[0_20px_60px_-15px_rgba(16,30,51,0.2)]` on the inner content box (already `overflow-hidden`, so the header/body/footer's square edges clip cleanly to the new rounded corners with no other changes needed). Left below `lg:` untouched — the mobile full-screen slide-in sheet stays flush/edge-to-edge, which is the right shape for that presentation; rounding a panel that's flush against every viewport edge wouldn't read as "a block," it'd just clip content.
